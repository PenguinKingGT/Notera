# Notera 产品与架构范围（确认稿）

状态：用户通过 Q33 确认本稿的范围与实施顺序，开始第一阶段风险验证。实现建议作为初始方案，具体引擎、数据结构和准确度门槛由验证结果确定。

## 产品目标与约束

- 面向个人创作者，完成输入、修改、试听、导出的完整流程。
- 改善 MuseScore 的 UI/UX，优先连续输入与修改体验；接近 Dorico 的排版能力是长期目标。
- 首版以 macOS 钢琴五线谱为主，在有限记谱范围内做好自动排版。
- 项目开源，主要由作者开发，按个人长期维护设计。
- 不自行编写 C++；可以编写 Rust，接受成熟工具内部使用其他语言。
- 使用 Electron、Vite、React、TypeScript、shadcn/ui 和 pnpm，以独立乐谱文件持久化。

## 已确认的首版范围

### 五线谱编辑与播放

- 钢琴双谱表、多声部、和弦、常用时值与附点、三连音、调号、拍号、连线、力度、踏板和反复记号。
- 鼠标点谱与电脑键盘快捷输入，优先连续输入和修改体验。
- 钢琴试听、播放控制、速度调整与谱面跟随；力度和踏板参与播放。
- 装饰音、跨谱表符杠、复杂嵌套连音等逐步扩展；遇到暂不支持的内容明确提示。

### 简谱视图

- 五线谱与简谱共享音乐内容，五线谱修改后简谱同步更新。
- 保留完整双手、和弦与多声部，首版用于查看和 PDF 导出，编辑在五线谱中完成。
- 左右手分别成组，声部使用独立行，和弦数字纵向叠放，同时发生的音乐按拍点对齐。
- 五线谱与简谱分别排版、分页，不要求页面一一对应。

### 文件与恢复

- 五线谱支持 MusicXML 导入、MusicXML 导出和 PDF 导出；简谱支持 PDF 导出。
- 手动保存更新正式文件，后台维护独立恢复副本，重启后提供恢复入口。
- 关闭有未保存修改的乐谱时，提示保存、放弃或取消关闭。
- 原生文件字段、版本迁移与 MusicXML 支持矩阵在模型设计阶段明确。

### AI 识谱

- 支持五线谱截图、多张图片和 PDF；一次任务对应一份乐谱。
- 图片允许排序，PDF 按页序处理，不同曲子分别导入。
- 使用用户自己的 API Key，支持 OpenAI 兼容接口和 Claude；服务地址与模型可配置。
- 检测各服务实际支持的图片、PDF 和结构化结果能力。
- 识别结果转换为普通原生乐谱，与新建乐谱使用相同模型和编辑能力。
- 无需原图对照界面或专门校对流程；暂不接入自然语言修改乐谱。
- 部分页失败时保留成功结果，提示失败页并允许单独重试；生成的乐谱可继续编辑。
- 重试保留用户修改，只加入失败页结果；可能重复或覆盖时由用户选择合并。
- 来源页用于识别顺序和重试定位，谱面页由排版产生，两者不直接绑定。

## 已确认的架构原则

- 乐谱模型独立于 React、Electron、排版引擎和 AI 服务。
- 优先复用成熟排版能力，以钢琴谱例验证候选引擎后再选择具体依赖。
- 排版关注间距、碰撞、分页与编辑后的重排；不承诺首版达到 Dorico 的完整能力。
- Rust 根据经验证的性能或算法需求引入，当前不预设职责。

## 建议的模块边界

以下是经 Q33 整体确认的初始实现方案，细节可根据验证结果调整。

| 模块     | 职责                                                                                |
| -------- | ----------------------------------------------------------------------------------- |
| 乐谱核心 | 音高、节奏、谱表、声部、记号、稳定标识、编辑命令和撤销/重做；音乐语义独立于绘制坐标 |
| 排版适配 | 音乐内容到布局、可选中对象及命中区域；分别支持五线谱与简谱                          |
| 编辑界面 | React 与 shadcn/ui 管理工具栏、面板、输入状态和快捷操作；谱面由排版层呈现           |
| 文件交换 | 原生文件版本、迁移、校验，MusicXML 导入导出及不支持内容报告                         |
| 播放     | 播放事件、速度、力度、踏板、支持的反复与播放位置                                    |
| 识谱服务 | 服务适配、任务状态、结果校验、来源追踪、失败页重试和合并                            |
| 桌面服务 | 主进程负责文件、凭据及外部模型调用，经窄 preload API 暴露能力                       |

建议原生文件先采用带版本号的 JSON，库索引有实际需求后再考虑 SQLite。
API Key 建议使用系统凭据保护机制，模型调用留在主进程或其受控工作进程；凭据不进入乐谱文件或日志。
识谱重试建议以来源片段标识及版本检测保护手动修改，无法安全合并时交由用户确认。
输入状态机、合并粒度、运行线程和库版本属于后续设计任务。

## 建议的验收方式

### 编辑与文件

- 打通“新建 → 连续输入 → 修改 → 撤销/重做 → 保存 → 重开 → 播放 → 导出”。
- 保存和重开保留支持的音乐内容；撤销/重做同时恢复音乐与视图。
- 验证关闭取消、保存失败、损坏文件和恢复副本；恢复不静默覆盖正式文件。
- MusicXML 按首版支持矩阵验收往返，无法保留的内容明确报告。

### 排版与简谱

- 使用人工确认的钢琴谱例，覆盖双谱表、多声部、和弦、临时升降号、附点、三连音、连线、力度、踏板和反复。
- 检查间距、碰撞、跨行处理、页面密度及插入/删除后的重排。
- 简谱保留左右手、声部、和弦、音区与节奏，五线谱编辑后同步更新。
- 性能目标和视觉容差在引擎原型阶段结合谱例规模确定，当前不虚设数值。

### AI 识谱

- 建立截图、多图片及多页 PDF 的人工标注基准，按服务与模型报告音高、时值、声部、记号和页面成功率。
- 结构化结果经过音乐语义检查；格式合法不代表识谱准确。
- 成功结果正常编辑，失败页可单独重试，重试不静默覆盖手动修改。
- 准确度门槛根据原型实测和目标谱例确定，再决定是否达到发布条件。

## 建议的实施顺序

1. **验证关键风险**：同一组钢琴谱例验证排版候选、编辑对象映射及 AI 识谱质量；明确依赖许可证约束。
2. **建立音乐核心**：支持矩阵、领域模型、命令与撤销/重做、原生文件及版本迁移。
3. **打通五线谱编辑**：新建、连续输入、修改、排版、保存/恢复和 MusicXML 交换。
4. **完成试听与五线谱导出**：播放、谱面跟随、力度/踏板/反复及 PDF。
5. **接入识谱流程**：服务配置、输入排序、任务校验、失败页重试与编辑保护。
6. **完成简谱与发布验收**：多声部简谱、PDF、回归谱例和 macOS 打包。

## 待后续验证或设计

- VexFlow、Verovio 等候选的排版质量、编辑集成成本和许可证；尚未选定引擎。
- 多声部简谱的音级、音区、延音线和跨行等详细规则。
- 各 AI 服务的输入能力与识谱质量；尚未指定默认模型。
- 开源许可证、macOS 签名与分发方式，在确定依赖及发布计划时决策。
