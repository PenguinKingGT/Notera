# AI 识谱服务能力与验证方案

核对日期：2026-10-04。阶段：第一阶段风险验证。

本报告核对官方 API 文档，未调用模型、读取密钥或测量识谱准确度。协议支持以当前官方服务为基准；第三方兼容服务及用户选择的模型仍需实测。不指定默认模型。

## 结论与证据边界

OpenAI 和 Claude 的官方接口提供图片、多图片、PDF 与结构化输出入口，具体形式见下表。[OpenAI 图片][openai-vision]、[OpenAI 文件][openai-files]、[OpenAI 结构化输出][openai-structured]、[Claude 图片][claude-vision]、[Claude PDF][claude-pdf]、[Claude 结构化输出][claude-structured]

这些文档不能证明五线谱识别准确度。OpenAI 明确说明视觉模型及结构化输出仍可能出错；Claude 结构化输出约束的是响应格式。[OpenAI 视觉限制][openai-vision]、[OpenAI 输出错误][openai-structured]、[Claude 输出格式][claude-structured]

**工程判断：JSON 可解析、符合 Schema、能够生成谱面，均不等于音高、时值、声部和记号正确。** 是否达到 Notera 的要求，必须使用人工标注的钢琴谱例评估。以下验证建议尚未执行，也不构成准确率承诺。

## 协议输入与输出矩阵

| 协议                        | 单图与多图                                                                                 | PDF                                                            | JSON 结构化输出                                                                           |
| --------------------------- | ------------------------------------------------------------------------------------------ | -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| OpenAI Responses            | `input_image`；URL、Base64 数据 URL 或文件 ID；同一内容数组可放多图。[来源][openai-vision] | `input_file`；Base64、文件 ID 或文件 URL。[来源][openai-files] | `text.format` 的 `json_schema`，配合 `strict`。[来源][openai-structured]                  |
| OpenAI Chat Completions     | `image_url`；URL 或 Base64 数据 URL；内容数组可放多图。[来源][openai-vision]               | `file`；Base64 或文件 ID；不支持文件 URL。[来源][openai-files] | `response_format` 的 `json_schema`，配合 `strict`。[来源][openai-structured]              |
| Claude Messages（直接 API） | `image`；Base64、URL 或 Files API 文件 ID；多图可联合分析。[来源][claude-vision]           | `document`；Base64、URL 或文件 ID。[来源][claude-pdf]          | `output_config.format` 的 `json_schema`；工具参数另用 `strict`。[来源][claude-structured] |
| 第三方 OpenAI 兼容服务      | 图片格式、数量及视觉模型支持待实测                                                         | 文件输入、URL、上传端点及 PDF 视觉解析待实测                   | Schema、严格模式及响应错误处理待实测                                                      |

最后一行为验证要求，不能从“兼容”声明推导功能齐全。适配配置应显式记录协议家族、服务地址和模型；同一服务分别验证 Responses 与 Chat Completions 能力，不能只修改地址便假定互通。

## 官方限制及适配建议

- OpenAI PDF 的视觉解析需要支持视觉的模型，输入包含提取文本与页图。每个文件须小于 50 MB，一次请求全部文件合计最多 50 MB。[来源][openai-files]
- OpenAI 视觉文档列出小文字、旋转、精确空间定位与计数限制，并说明图像可能缩放。[来源][openai-vision]
- Claude 直接 API 单图上限为 8000 × 8000 像素、Base64 编码图片最大 10 MB；图片数量上限随模型上下文变化，超过 20 图还涉及更严格尺寸限制；图片可能缩小处理。[来源][claude-vision]
- Claude PDF 输入包含页图与文本；要求标准且无密码或加密。标准端点请求上限为 32 MB，页数上限为 600，低于 1M token 上下文时为 100；上下文可能先耗尽。[来源][claude-pdf]
- 两家结构化输出均有 Schema 支持范围和模型适用条件。拒绝或输出截断需要单独处理；Claude 还列出枚举大小写等例外。因此响应完成后仍应执行本地校验。[OpenAI][openai-structured]、[Claude][claude-structured]

**建议：**能力检测区分“请求接受”“输出可解析”“音乐内容正确”。明确记录图片数量、尺寸、请求体和上下文限制，不将官方最大值直接设为识谱批量大小。原生 PDF 不可用时，可验证本地分页栅格化后按顺序送图的路径；其识谱质量和资源成本仍需单独测量。

## 可复现的钢琴谱例评估

以下为建议方案，范围遵循[产品规格](../spec.md)与[独立乐谱模型 ADR](../../../docs/adr/0002-independent-score-model.md)。人工标注用于研发评估，不要求产品增加原图校对视图。

### 数据与运行记录

1. 使用自行编写或获准使用的钢琴谱例，人工标注为独立于模型的标准答案，再复核。覆盖双手、和弦、多声部、休止、附点、三连音、调号、拍号、临时升降号、延音线、连奏线、力度、踏板与反复记号；复杂连音、装饰音、跨谱表连梁另列为暂不支持的边界样例。
2. 标注谱表、声部、起始位置、有理数时值、音名/变音/八度、和弦关系及记号的锚点或跨度。区分延音线与连奏线，保留跨来源页关系。声部编号先规范化，避免等价编号差异被当成音乐错误。
3. 同一内容制作截图、多张有序图片和 PDF；清晰输入与低分辨率、旋转、拍照透视分别成组。记录文件哈希、来源页 ID、页序、图像尺寸及 PDF 栅格化参数，不混合统计不同质量输入。
4. 固定提示词、Schema、协议、预处理和请求参数，每种组合建议独立运行至少三次。记录服务、模型返回标识、时间、结束原因、耗时、用量、错误及经脱敏的原始结果；不得记录 API Key。人工修正后的结果不计入模型原始成绩。

### 指标与判定

| 指标         | 建议定义                                                                                            |
| ------------ | --------------------------------------------------------------------------------------------------- |
| 结构通过率   | 完整返回、JSON/Schema 通过及领域校验通过的比例，三层分别报告；领域校验含时值规则、引用与跨页关系    |
| 页成功率     | 无需人工修正且与标准答案在支持范围内完全一致的来源页数 / 全部评估来源页数；请求失败及漏页也计入分母 |
| 音高         | 对齐事件后分别统计实际音高与记谱拼写的正确率，并报告漏音、增音及 precision/recall/F1                |
| 时值         | 起始位置与有理数时值的精确匹配率；休止、附点与三连音单独统计                                        |
| 谱表与声部   | 双手谱表归属、规范化声部分配及同时发声关系的正确率                                                  |
| 记号         | 调号、拍号、力度、踏板、反复以及连线类型、起止锚点的 precision/recall/F1                            |
| 整任务完整率 | 来源页顺序、页间音乐连续性及跨页记号都正确的识谱任务比例                                            |

事件匹配规则应在运行前固定；使用小节位置、谱表及事件序列辅助对齐，不以“预测音高已经正确”作为匹配前提。遗漏和重复必须计错，不能只评估成功匹配的音符。逐页和逐特征报告结果，避免简单谱或音符密集页掩盖困难样例。验收阈值待实测后讨论，不在本报告虚设达标数值。

来源页是输入追踪单位，谱面页是自动排版产物，二者不能混用。结构通过而内容错误的页须单独列出；模型自报置信度不能替代标准答案。

## 失败来源页重试与修改保护

以下为实现建议，目标是让结果成为普通可编辑乐谱，同时允许单页恢复：

- 为识谱任务、来源页和重试建立稳定 ID；记录来源顺序、每次尝试及发起时的乐谱修订号。成功部分保留，失败页保持可定位状态；不因漏页悄悄重排来源映射。
- 将响应先转换成待合并音乐内容，执行结构及领域校验后提交。一次尝试只提交一次；取消或过期请求的迟到结果不能覆盖新尝试，重复响应不能重复插入音乐。
- 重试只针对失败来源页及必要的页间上下文。合并按来源映射和音乐实体定位，不按当前排版后的谱面页替换。
- 检查目标内容自发起后是否被编辑、移动或删除。存在冲突时保留用户修改并要求明确选择合并方式；跨页连线与小节连接也须重新校验。合并应成为可撤销的编辑操作。
- 验证“部分成功后手工修改，再重试失败页”“取消后迟到”“连续重试两次”“编辑跨页连线”“保存后重新打开”等场景；网络或内容失败不得破坏已有乐谱。

## 下一步验证与未解决问题

先以本地样例和模拟响应验证协议编码、Schema、错误分类及合并保护。后续实际服务评估需使用用户选定的服务和模型，记录矩阵中每项实测支持情况，再运行上述谱例；本报告未完成此项。

尚无证据证明：多模态 Agent 达到所需钢琴识谱质量、复杂多声部能完整恢复、跨来源页记号稳定、第三方兼容端点等同官方能力。只有实测结果能决定是否满足有限范围高质量目标。
